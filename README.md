# Baal Dan Charities Website Redesign

A modern, donation-ready redesign of [baaldan.org](https://www.baaldan.org/) built to the visual and UX standard of large nonprofit sites (full-bleed photographic heroes, animated impact stats, program cards, testimonial carousel, transparency callouts), with all of the original site's content preserved and reorganized. The visual language, Baal Dan's own navy blue and flower mark (sampled directly from their logo), a warm clay accent for calls to action, bold sans-serif type, documentary photography, takes cues from international NGO sites like [farmafrica.org](https://www.farmafrica.org/) while staying true to the org's real brand identity.

Pure static HTML/CSS/JS: **no framework, and no dependencies beyond Node.js itself.** The one small build step (`npm run build`) merges CMS-editable content into the static pages; the output in `dist/` can be dropped on any static host.

## Structure

```
index.html            Home
about.html             About Us, Our Grassroots Approach, About Tanya Pinto, Our Team
programs.html          What We Fund (food / education / WASH) + Grantee Partners
impact-news.html       Transparency & impact stats, Events & Fundraisers, News
donate.html            Donation flow, ways to give, employee matching, testimonials, FAQ
little-hero-film.html  Little Hero short film
contact.html           Contact form + Copyright & Privacy

content/               CMS-editable records (see Editing content below)
.pages.yml             Pages CMS form definitions
scripts/               Build & validate scripts that turn content/ into dist/
dist/                  Deployable, built site (generated by `npm run build`, not committed by hand)

assets/css/style.css   Design system (colors, type, components)
assets/js/main.js      All interactivity (nav, dark mode, counters, slider, accordion, donate form)
assets/img/            Hero and feature photography (see Photography below)
assets/data/content.json  Impact stats, testimonials, news items, and the upcoming event (regenerated by the build)
partials/header.html   Shared header, injected client-side via fetch()
partials/footer.html   Shared footer, injected client-side via fetch()
```

## Running locally

Run `npm run build` first (see below), then serve `dist/` with a local static server &mdash; the header/footer partials and `assets/data/content.json` are loaded via `fetch()`, which `file://` blocks in most browsers:

```bash
npm run build
python3 -m http.server 8080 --directory dist
# or: npx serve dist
```

Then visit `http://localhost:8080`.

While actively editing the *source* HTML/CSS/JS (not the generated content), you can also serve the repository root directly the same way; the pages will show whatever placeholder copy is currently baked into the markup instead of live CMS content.

## Features

- Responsive, accessible nav with dropdowns and a full-screen mobile menu
- Light/dark mode toggle (persisted in `localStorage`)
- Animated impact counters, scroll-reveal animations (progressive enhancement: content is fully visible with JavaScript disabled)
- Testimonial carousel, FAQ accordion, tap-to-expand country cards
- Donation panel: amount + frequency selection with live "your impact" messaging
- Employee matching-gift lookup (demo logic, see below)
- Newsletter and contact forms (demo, see below)

## Going live with real donations

The donate flow is fully built out on the front end but intentionally **does not move real money yet**. That requires the organization's own payment credentials, which weren't available to wire up. To connect it:

1. Open `donate.html` and find:
   ```html
   <form id="donate-form" data-paypal-business="REPLACE_WITH_PAYPAL_BUSINESS_EMAIL">
   ```
   Replace the placeholder with Baal Dan's PayPal business email. The form already posts to PayPal's standard `cmd=_donations` endpoint with the selected amount. No API keys needed.
2. For a card-based experience instead, swap the submit handler in `assets/js/main.js` (`initDonateForm`) to redirect to a Stripe Payment Link, or embed Stripe Checkout / PayPal Donate SDK directly.
3. The employee-matching search (`initMatchSearch` in `main.js`) and the newsletter/contact forms (`data-demo-form`) are currently front-end demos that show a confirmation toast. Wire them to a real matching-gift provider (e.g., Double the Donation) and an email/CRM endpoint (e.g., Formspree, a serverless function, or your ESP's API) respectively.

## Content

All copy, statistics, testimonials, grantee partners, news items, and bios were pulled directly from the live baaldan.org site (as of July 2026) and preserved, reorganized into a cleaner information architecture, but nothing removed.

## Photography

The photos in `assets/img/` are free-to-use stock images from [Unsplash](https://unsplash.com) (Unsplash License: free for commercial and non-commercial use), chosen to represent the regions and program types Baal Dan funds. None depict actual Baal Dan staff, donors, or beneficiaries. Swap them for real program photography as it becomes available. Every hero image is set via a single CSS rule (e.g. `.hero-home`, `.hero-about` in `assets/css/style.css`), so replacing a file is a one-line change.

## Structured content

- `content/testimonials/` contains one JSON record per donor testimonial (quote, name,
  role, whether it's featured in the homepage slider, and display order).
- `content/news/` contains one JSON record per "News From the Field" item.
- `content/partners/` contains one JSON record per grantee partner.
- `content/countries/` contains one JSON record per country we work in, with separate
  fields for the short homepage teaser blurb and the longer WASH/grant details shown
  on the Programs page.
- `content/pages/` contains one JSON file per page (`home.json`, `about.json`,
  `programs.json`, `donate.json`, `impact-news.json`, `contact.json`,
  `little-hero-film.json`) with that page's editable heading/paragraph/button text.
- `content/settings/global.json` holds sitewide text and links reused in the footer
  and elsewhere (tagline, copyright line, social links, and the PayPal business email
  used on the Donate page).
- `content/settings/stats.json` holds the impact-stat numbers shown across the site
  (children supported, countries reached, overhead rate, etc.).
- `content/settings/event.json` holds the single upcoming fundraiser/event.
- `.pages.yml` defines the editing forms used by [Pages CMS](https://pagescms.org/).
- `assets/img/uploads/` stores images uploaded through the CMS.

Run `npm run content:validate` after changing records by hand. It checks required
fields, duplicate slugs, URL formats, and that every `cms:` marker in the HTML
resolves to a real content field.

### How page text becomes editable (the `cms:` marker convention)

Most of each page's prose (headings, ledes, button labels, CTA text) lives directly
in the root HTML files, wrapped like this:

```html
<h1><!-- cms:contact.hero_heading -->Contact Us<!-- /cms:contact.hero_heading --></h1>
```

The part between the two comments is the *only* thing that changes &mdash; the
`cms:contact.hero_heading` marker itself is permanent scaffolding, not content.
`npm run build` reads `content/pages/contact.json`'s `hero_heading` field and swaps
in whatever text is stored there, leaving the markers in place so the page stays
editable on every future build. Markers named `cms:global.*` pull from
`content/settings/global.json` instead of a page file.

Two related conventions handle content that isn't a plain text node:

- **Repeating sections** (the grantee-partner grid on `programs.html`, the country
  grids on `index.html` and `programs.html`) are wrapped in
  `<!-- cms:collection:name --> ... <!-- /cms:collection:name -->` and are fully
  regenerated at build time from `content/partners/` and `content/countries/`.
- **Attribute values** that aren't visible text &mdash; the PayPal business email in
  `donate.html`'s form, and the social links in the footer and Contact page (marked
  with `data-cms-social="facebook_url"` etc.) &mdash; are substituted directly by the
  build script from `content/settings/global.json`, since HTML comments can't sit
  inside an attribute value.

This is intentionally plain string substitution &mdash; no templating engine. That
makes it easy for a future AI coding session, or anyone editing by hand, to:

- **Add a new editable field to an existing page**: wrap the text in
  `<!-- cms:pagename.new_field_name -->...<!-- /cms:pagename.new_field_name -->`
  in the HTML, add `new_field_name` to the matching file in `content/pages/`, and
  add a matching entry under that page's `fields:` list in `.pages.yml`.
- **Add a whole new editable page**: create `content/pages/<slug>.json` with a
  `slug`/`published` plus whatever fields it needs, wrap the corresponding HTML in
  `cms:<slug>.field` markers, and add a `type: file` entry to `.pages.yml` pointing
  at it (copy one of the existing `*-page` entries as a template).
- **Not everything needs to be a CMS field.** Impact stats, testimonials, news, and
  the upcoming event already have their own runtime mechanism: `assets/js/main.js`
  fetches `assets/data/content.json` (regenerated by the build from
  `content/testimonials/`, `content/news/`, `content/settings/stats.json` and
  `content/settings/event.json`) and renders it client-side, so those static
  placeholder cards in the HTML source are a pre-JS fallback only, not directly
  CMS-managed. Likewise, content that changes only via a real code change (the
  icon-driven feature-card grids, the FAQ answers, the amount buttons on Donate) is
  left as plain HTML on purpose; editing it directly in the HTML is simpler than
  adding a form field for something that rarely changes and has real layout
  attached to it.

`npm run content:validate` scans every root HTML file and partial for `cms:` markers
and checks that each one resolves to a real field &mdash; a typo'd or renamed marker
fails validation instead of silently leaving stale text on the live site.

Run `npm run build` to create the deployable site in `dist/`. Static hosting (or the
included GitHub Actions workflow) should publish the `dist/` directory, not the repo
root.

## Editing content (no code required)

Editing is done through [Pages CMS](https://pagescms.org/), a free, git-backed CMS
that reads the `.pages.yml` file at the root of this repo: a plain form UI, and every
save is a real commit straight to this repository. Unlike the previous Decap CMS
setup, Pages CMS authenticates with its own GitHub App, so there's no Netlify relay
or OAuth app of your own to configure.

### One-time setup (do this once, not per edit)

1. Go to [app.pagescms.org](https://app.pagescms.org) and sign in with GitHub.
2. Install the **Pages CMS GitHub App** on the `prahaladtalur/baaldan` repository
   (Pages CMS will prompt for this on first use).
3. Select this repository and the `main` branch. Pages CMS reads `.pages.yml`
   automatically and builds the editing forms from it.
4. Bookmark the resulting `app.pagescms.org/...` editing URL for whoever maintains
   the site.

After that one-time setup, editing is just: open the bookmarked link, pick a page,
testimonial, news item, partner, or country from the list, edit the fields, and
save. Changes commit straight to `main`; if the GitHub Actions workflow in
`.github/workflows/deploy-pages.yml` is enabled for this repo (Settings → Pages →
Source → GitHub Actions), the live site rebuilds and republishes automatically
within about a minute. Until then, or for any other host, run `npm run build` and
publish the resulting `dist/` folder yourself.
